# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Rebuild of https://www.adoptii-animale-hope.org (animal protection association HOPE, Bucharest), currently hosted on Wix. The new site must keep the same pages, content and search ranking, and adds a small admin to manage animals. The project owner communicates in French.

## Rules

- **Everything technical is in English**: identifiers, database values, tags, filter values, code comments, CLI messages. Human-facing labels are translated by the front end from those identifiers (`src/lib/taxonomy.ts`).
- **Animal names are never translated.** `animals.name` is deliberately outside the translations table. The Wix auto-translations mangled several names ("Brownie" → "Brown", "Patraulea" → "Patrol"); do not reintroduce that.
- **SEO parity is the main constraint.** URLs must stay identical to the Wix site: Romanian at the root, other languages under `/en`, `/fr`, `/de`, same slugs in every language, no trailing slash. `migration/seo-baseline.json` is the reference for titles, descriptions, h1, canonical and hreflang of all 351 existing URLs. Slugs imported from Wix are kept as-is even when odd (`/adoptii-pisici/-marzipan`, `/adoptii-virtuale-pisici/garfields`).
- **A page looks the same in every language.** Layout and styles never depend on the locale. When a page reads better in one language, the cause is its stored HTML (Wix kept a different structure per language), so fix the structure, not the stylesheet: `structureBody` (`src/lib/page-body.ts`) handles the patterns that can be detected, a structured file in `migration/translations/{locale}/pages/` the rest. `pnpm pages:check` must report no difference, and any change to content pages is checked visually in the four languages.
- **Visual identity is the Wix one, modernised.** Keep the palette (green, teal, orange, sand: the tokens at the top of `src/styles/global.css`; teal is the main colour of the `classic` theme and reaches the stylesheet as `--primary`), Poppins for text, menu and buttons, Fredoka 600 for titles (`--font-title`, chosen by the owner for its rounded shapes), and the curved edges between sections. The title band of every page has the ground of the home hero (gradient, paw prints, soft light). The bright logo green (`--green`) is for small accents only; large surfaces use `--green-deep` or teal. Titles must stand out (bold, type scale tokens) and running text stays at weight 400. Proposals for other directions live in an artifact, not in the code.
- An animal is either a real adoption or a virtual one (`adoptionType`: `real` | `virtual`), never both.
- A hook blocks `rm -rf`; use `gio trash` instead.

## Commands

```bash
pnpm dev                 # dev server
pnpm build               # astro check + build (type errors fail the build)
pnpm check               # type check only
pnpm start               # run the built server (dist/server/entry.mjs)
pnpm db:generate         # generate a migration in drizzle/ after editing src/db/schema.ts
pnpm db:migrate          # apply migrations
pnpm user:create --email a@b.org --name "Name" --locale ro|fr   # create an admin account from the terminal (the first one; the others are created in /admin/users): password + authenticator app (QR code in the terminal)
pnpm user:reset --email a@b.org    # new password and new authenticator app for an existing account, when nobody can sign in any more
pnpm crawl [--media] [--refresh]   # re-crawl the Wix site into migration/
pnpm import:animals [--dry-run]    # import migration/wix-export/*.csv (replaces all animals)
pnpm import:pages [--dry-run]      # import content pages from the crawl (replaces all pages, so run import:translations again afterwards)
pnpm import:memoriam               # create the deceased animals of the Wix "In memoriam" page (run after import:animals)
pnpm import:translations           # import migration/translations/ (German texts, missing EN/FR, corrections) — run after the other imports
pnpm seo:fill [--dry-run]          # fill empty SEO title/description of animals in every language (never overwrites)
pnpm seo:check [--url <origin>]    # compare a running server (default http://127.0.0.1:4321) with migration/seo-baseline.json
pnpm pages:check                   # every content page must have the same headings and images in the four languages
pnpm test                          # unit tests in tests/*.test.ts (Node test runner): donations, campaigns and the Stripe webhook, contact form, sign-in (TOTP, sessions, throttling), accounts, content page admin
pnpm test:server                   # builds, then tests/server/: the built server on a scratch database (redirects, headers, form posts, contact, admin sign-in, accounts, page SEO, campaigns and webhook)
```

Scripts in `scripts/` run directly with Node 24 (native type stripping): relative imports need the `.ts` extension, and no path aliases, enums or parameter properties. Tests follow the same rules and never call an external service (`fetch` is mocked for Stripe). A test that writes imports `tests/helpers/scratch.ts` first: it points `DATABASE_PATH` and `DATA_DIR` at a temporary directory and applies the migrations. `tests/server/` starts `dist/server/entry.mjs` on that scratch database, because the middleware only exists in the build; Node's `fetch` always sends `Accept-Language: *`, which must not trigger the language redirect.

## Deployment (`deploy/`)

Two Node workers under PM2 in cluster mode (a reload replaces them one after the other, without downtime; `src/lib/shutdown.ts` lets an old worker finish its requests), behind nginx, behind Cloudflare, which holds the public certificate. `deploy/README.md` (French) is the procedure.

- `install.sh` (root, once) prepares the VPS and installs the `hope-deploy` command, which runs the `deploy.sh` of the main branch. `deploy.sh` builds each version in `/srv/hope/releases/`, snapshots the database, applies the migrations, switches the `current` symlink and reloads PM2; `--rollback` goes back one release. Configuration, database and uploads live in `/srv/hope/shared/` and are never replaced by a deployment; `push-data.sh` sends the local database and uploads there.
- `backup.sh` runs every night from `/etc/cron.d/hope-backup`: a verified copy of the database, the uploads and the contact attachments in `shared/backups/daily/<date>-<time>/` (unchanged files are hard links to the previous backup, `BACKUP_KEEP` kept), then copied to `BACKUP_REMOTE` (rsync destination in `shared/.env`) when it is set. A new directory of data that cannot be rebuilt must be added to its list.
- `setup-nginx.sh <domain>` generates the nginx configuration: only Cloudflare addresses are answered, the visitor's address comes from `CF-Connecting-IP`, and any domain other than the production one is served `noindex`.
- Astro trusts the proxy headers only for the hosts in `security.allowedDomains` (`astro.config.ts`): the production host and the host of `SITE_URL` at build time. Without it form posts answer 403 behind the proxy and every visitor shares one address for the rate limits. nginx replaces `X-Forwarded-For` rather than extending it, because Astro reads its first value.
- Because there are two workers, anything kept in memory is per worker: the rate limits (login, contact form) are counted separately in each, and shared state must go to the database or to files written aside and renamed (as the image cache does).
- The scripts contain `rm -rf`, so the local hook refuses a shell command that writes them: edit them with the file tools.

pnpm must be allowed to build `better-sqlite3` and `esbuild` (`pnpm-workspace.yaml`). TypeScript is pinned to 6.x because `@astrojs/check` does not support 7.

## Architecture

Astro in server mode (`@astrojs/node`, standalone) with SQLite through `better-sqlite3` and Drizzle. Target hosting is a VPS; the database is a single file (`DATABASE_PATH`, default `data/hope.db`) and uploads live in `data/uploads/`, both outside git.

- `src/lib/taxonomy.ts` — controlled vocabularies (species, adoption type, sex, size, colour, traits, status) and the collection → URL segment map. The schema enums are built from these arrays, so adding a value means editing this file and generating a migration.
- `src/db/schema.ts` — `animals` holds the structured, filterable data (one colour identifier, booleans `vaccinated`/`sterilized`/`dewormed`, `birthDate`). Traits are many-to-many in `animal_traits`. Only free text is translated (`animal_translations`: description and SEO fields per locale).
- Age is never stored: it is computed from `birthDate` (`ageInMonths`). `birthDateEstimated` marks dates derived from a Wix age such as "3 ani" (counted back from the record's last Wix update) rather than from a real month of birth.
- `src/i18n/config.ts` — public locales (`ro`, `en`, `fr`, `de`), admin locales (`ro`, `fr`), and path helpers. `ENABLED_LOCALES` lists the languages actually served (all four); a language missing from it answers 404 and is left out of hreflang, sitemap and the language menu.
- `src/i18n/ui.ts` — every interface string and taxonomy label in the four languages, including gendered forms (`[masculine, feminine]`) picked from the animal's sex. `seo.descriptions` gives each page its own meta description in English, French and German (Romanian keeps the Wix ones, checked by `pnpm seo:check`); `photoAlts` holds the alternative text of the photos shown by the templates, by file name.
- `src/pages/[...path].astro` — the single entry point of the public site: it splits the language prefix, resolves home / collection list / animal / content page / contact / 404, and computes the SEO tags. `src/layouts/Base.astro` renders head (canonical, hreflang, Open Graph), header, the shared call-to-action tiles and footer.
- `src/lib/json-ld.ts` — structured data of the public pages, in the language of the page: the association (`AnimalShelter`) and the site (`WebSite`) on the home page, then on every indexable page the page itself (`WebPage`, `CollectionPage` for lists, `AboutPage`, `ContactPage`) and its breadcrumb. Pages that are `noindex` (404, filtered lists, post-payment pages) have none.
- `src/middleware.ts` — redirects (trailing slash, `/_files/ugd/*` → `/files/*`, `/ro/*` → the same path without prefix, the Wix `*-sitemap.xml` files → `/sitemap.xml`, `LEGACY_REDIRECTS` in `src/lib/site.ts`, then the `redirects` table; the dev server answers 404 to a trailing slash before the middleware runs, so test redirects on the build) and security headers. HTML answers `Cache-Control: no-cache` (`no-store` in the admin) and, on the build only, a `Content-Security-Policy` that allows nothing but the site itself: every inline `<script is:inline>` and `<style is:inline>` must carry `nonce={Astro.locals.cspNonce}`, stylesheets are never inlined (`build.inlineStylesheets`), public pages have no `style` attribute (the admin may), and a new external origin (script, image, embed, form target) must be added to `contentSecurityPolicy`. Check a change of that kind in a browser on the build: the dev server does not send the policy.
- Images are served by `/media/{animals|pages|campaigns}/{width}/{file}`: resized to WebP with sharp on first request and cached in `data/cache/`. Only the widths in `IMAGE_WIDTHS` (`src/lib/media.ts`) exist. Videos and documents are streamed from `data/uploads/` with Range support.
- Each URL has one language. On the first visit only (no `lang` cookie), the middleware answers 302 to the version matching `Accept-Language` (English when none of the browser languages is served), then sets the cookie so the language switcher is never overridden. Requests without `Accept-Language` are never redirected: that is what keeps every language crawlable by search engines, so do not add a default redirect for a missing header and do not move this logic to client-side JavaScript (Googlebot renders it).
- Admin (`src/pages/admin/`): server-rendered pages that handle their own form POSTs in the frontmatter, no client framework. The middleware guards every `/admin` path except `/admin/login` and exposes the signed-in user as `Astro.locals.user`. Signing in always needs password + TOTP code from an authenticator app (`src/lib/totp.ts`, RFC 6238, no other second factor); both are enrolled together, and an account without a password hash or a TOTP secret cannot sign in. Sessions are random tokens stored hashed (`src/lib/auth.ts`); failed logins are throttled in memory per IP and per e-mail (per worker in production). Cross-site POSTs are rejected by Astro's `checkOrigin`, so tests with curl must send an `Origin` header. All writes go through `src/lib/admin-animals.ts`, which validates against the taxonomy, re-encodes uploaded images with sharp, and creates 301 redirects in every language when an animal's URL changes. Admin strings are in `src/i18n/admin.ts` (Romanian and French, chosen per user).
- Accounts (`/admin/users`, `src/lib/admin-users.ts`): every account has the same rights. Creating an account, or resetting one, never sets credentials: it cancels the old ones at once (empty password hash, new TOTP secret, sessions ended) and shows once a link to `/admin/setup?token=…`, valid 72 hours and stored as a SHA-256. On that page, the only admin path besides the login form that needs no session, the person chooses a password and confirms the authenticator app with a code; nobody else ever knows either. Nobody deletes their own account, and resetting one's own keeps the current session until the link is used. The CLI stays for the first account and as the way back in.
- Anomalies shown in the admin (list flag and box at the top of an animal's page) come from fixed rules in `src/lib/animal-checks.ts`, evaluated on the stored record at each display; nothing is persisted. To add a check: add a code to `ISSUE_CODES`, the rule in `checkAnimal`, and its message in both languages of `src/i18n/admin.ts`.
- On save, empty animal SEO fields are generated (`src/lib/seo.ts`); a field still equal to what was generated before the save is regenerated, hand-written values are kept.
- `DATA_DIR` (default `data`) holds uploads and the image cache, `DATABASE_PATH` the database: point both at a scratch copy to test admin writes without touching real data.
- Statuses: only `published` animals have a public page and appear in lists. `deceased` animals are listed on `/in-memoriam` (built from the database, the stored page body is ignored) and their former URL answers 301 to it. `draft` and `adopted` answer 404.
- Contact form (`src/components/ContactForm.astro`, `src/lib/contact.ts`): posted to the contact page itself, handled at the top of `[...path].astro`. The page has three moments: the reasons as tiles (radio buttons), the form sheet that appears once a reason is chosen (a guide with a link, then numbered parts; the cat questionnaire is the third), and the confirmation. Blocks marked `data-reasons` are shown for those reasons by the stylesheet (`:has()`), the script only disables and requires the matching inputs (`data-required-for`), so the form still works without JavaScript. Line icons shared with the tiles and the donation page are in `src/lib/icons.ts`. Messages are stored in `contact_messages`, listed in `/admin/messages`, and e-mailed when `SMTP_URL` is set. Stored option values are English identifiers; `describeContact` (`src/i18n/forms.ts`) renders them in any language. Spam traps: a hidden field and a minimum fill time (bots get the normal "sent" answer but nothing is stored), plus an in-memory rate limit per address. The `redirection` reason (reached from the redirection blocks with `?reason=redirection`) proposes a ready-made message and requires the filled-in form as an attachment: an image or a PDF of 5 MB at most, recognised from its content. It is stored in `data/contact/` (private, never under `uploads/`), attached to the notification e-mail and served to signed-in users only by `/admin/attachments/{id}`; deleting the message deletes the file. Other reasons have no attachment.
- Donations (`src/components/DonateForm.astro`, `src/pages/donate.ts`, `src/lib/stripe.ts`): the form posts to `/donate`, which creates a Stripe Checkout session with plain `fetch` (no SDK) and redirects there; `payment` mode for one-off gifts, `subscription` with an ad-hoc monthly price otherwise. Stripe is the record of donations; the webhook only counts the gifts made for a campaign. Without `STRIPE_SECRET_KEY` the donor is sent back with an "unavailable" notice.
- Fundraising campaigns (`src/lib/campaigns.ts`, `src/lib/admin-campaigns.ts`, `/admin/campaigns`): a campaign has a scope (`CAMPAIGN_SCOPES` in the taxonomy: `global`, `need`, `animal`, `event`), a status (`draft` | `published`) and is either permanent (no goal, no end) or temporary (`goalAmount` and `endsOn`, always set together). Public URLs are `/campanii` (list; `noindex` and out of the sitemap while no campaign is published) and `/campanii/{slug}`, same slug in every language; a language without a title shows the Romanian texts. A temporary campaign is closed when its goal is reached or after its last day in Romanian time (`campaignState`); it only takes one-off gifts in its own currency, so that the amount collected is exact, while a permanent one takes the whole donation form. The amount collected is the card donations recorded in `campaign_donations` plus `offlineAmount`, typed in the admin for transfers and cash. Open campaigns are shown on the home page (three at most), at the top of the donation page, in the footer links and, for an `animal` campaign, on the page of that animal; the header menu is left as on Wix. Pictures are in `data/uploads/campaigns` (image kind `campaigns`); an animal campaign without one shows the animal's photo. `<progress>` draws the bar, because public pages have no `style` attribute.
- Stripe webhook (`src/pages/stripe/webhook.ts`, `src/lib/stripe-webhook.ts`): the only POST of the site that is not a form (the middleware lets that path through). It trusts a request for its `Stripe-Signature` only (`STRIPE_WEBHOOK_SECRET`, 503 without it) and records the gifts whose metadata names a campaign: the paid Checkout session, then each later invoice of a monthly gift. Nothing about the donor is stored, and gifts without a campaign are not recorded: Stripe remains the record of donations.
- Donation page (`src/components/DonateMethods.astro`): the stored body of `/doneaza` is ignored. The page lists the ways of giving (`DONATION_METHODS` in `src/lib/site.ts`: card, bank transfer, PayPal, SMS, 3.5 % redirection) as anchors, then shows one section per method, all built alike. Bank accounts, SWIFT code and SMS number are in `SITE`; names, one-line summaries and the legal text of the SMS campaign are in `src/i18n/forms.ts` (`donate`). The beneficiary of a transfer is always the Romanian legal name, never a translation. `#card` is the anchor used by the Stripe return URLs and the sponsorship buttons.
- 3.5 % redirection ("formular 230"): `redirectCampaign` (`src/lib/redirect-form.ts`) gives the income year of the form and whether the online form of redirectioneaza.ro is open (1 January to 25 May, Romanian time). `RedirectActions.astro` shows the online button only during that period and the paper form all year. The redirection is presented in two versions only, both written in `src/i18n/ui.ts` (`homePage.redirect*`) so that every language says the same thing: the short block `RedirectSummary.astro`, identical on the home page and in the last section of the donation page, and the detailed version `RedirectDetail.astro`, which is the body of `/redirectioneaza` (the stored body of that page is ignored). Change the wording in those strings, never in one place only. `/formular-230.pdf` is ANAF's blank form (`src/assets/anaf-230.pdf`, first page) with the year and the association's details written in by `pdf-lib`; it is built once per year and served from `data/cache/forms/`. The field positions in `src/lib/redirect-form-pdf.ts` belong to that version of the form: when ANAF publishes a new one, replace the asset and check the positions on a rendered copy. Never write the year by hand in an interface string.
- Configuration is read through `env()` (`src/lib/env.ts`); see `.env.example`. `SITE_URL` overrides the public origin used in Stripe return URLs.
- List filters are plain GET parameters handled server-side and applied as soon as they change (the submit button only exists without JavaScript). Colour and trait take several values (repeated parameter, checkboxes in a `details`): values of one filter are alternatives, filters combine. A filter with a single possible value in a list is not shown; filtered URLs are `noindex` with the canonical pointing to the unfiltered list.
- Upload limits follow Cloudflare, which refuses a request above 100 MB: the animal form of the admin (photos of 15 MB, one video of 80 MB) refuses a selection above `MAX_UPLOAD_BYTES` (95 MB, `src/lib/admin-animals.ts`) before sending it, nginx accepts 100 MB under `/admin` and 8 MB elsewhere (the contact attachment is 5 MB), the Node adapter 100 MB (`bodySizeLimit` in `astro.config.ts`). Change them together.
- Every POST is an HTML form: the middleware answers 415 to any other content type or method, and its `redirect` helper never lets a target start with `//`.
- Content page admin (`/admin/pages`, `src/lib/admin-pages.ts`): the SEO title and description of the 13 content pages in the four languages (empty = the automatic value), and nothing else. The text of a page is neither shown nor edited in the admin, on the owner's decision (no HTML field, no visual editor): it changes through the files of `migration/translations/` and the import scripts. Those scripts replace the SEO fields written there: do not run `import:pages` or `import:translations` on the production database once the association edits them. Home, lists and contact keep their SEO texts in `src/i18n/ui.ts`.
- `redirects` table — 301/410 rules managed from `/admin/redirects`.
- `/shop` was published by mistake on Wix: it is not rebuilt and answers 410 (`REMOVED_PATHS` in `src/lib/site.ts`). The post-payment pages (`UNLISTED_PAGES`) are `noindex` and left out of the sitemap.
- Content pages: when the stored body has its own `h1`, it becomes the page heading instead of the UI label, so there is always exactly one `h1`. Romanian SEO title/description written by hand in Wix are imported from the baseline by `import:pages`.
- Every title band has one short sentence under its title (`.page-hero__lead`): `pageLeads` in `src/i18n/ui.ts` for content pages, `homePage.lead` (the mission) for the about page, the list leads for animal lists, the intro for contact, the explanation for the 404 page. A new page needs its sentence in the four languages.

- Content page bodies go through `structureBody` at display, in every language: bold-only or numbered short paragraphs become headings, lines starting with a dash become lists, and a document linked from its preview image at the end of a page becomes a `.download` block (preview, title, button). The stored body is not modified, so the rules survive a new import.
- Content pages have three presentations, chosen per page and never per language (`src/lib/site.ts`): the default white sheet over the title band; a photo beside the text for text-heavy pages (`PAGE_ILLUSTRATIONS`, file names from `data/uploads/pages`); a story for the sanctuary page (`STORY_PAGES`): an opening sheet with key figures, numbered chapters each beside its photo, a closing quote, all written as markup in the page files of the four languages. On a page with a photo beside the text, the photo that closes the stored body is taken out of the text (`splitClosingPhoto`): it goes under the illustration, and is the only photo when `PAGE_ILLUSTRATIONS` names that same file. Photos placed beside a text (these two layouts and the redirection block of the home page) always keep their own proportions: no `aspect-ratio` or cropping on them.
- Themes (`src/lib/themes.ts`, `/admin/theme`): a theme sets the main colour of the site (a gradient on the title bands, the footer and the other coloured grounds; its middle is `--primary`, used by titles, links, buttons and selected states, its start `--primary-dark`), the accent and the soft light used on those grounds, the colour of buttons and of the donation section of the home page (`call`, `--call` in the stylesheet: the Wix orange, except in `halloween` where it is night purple because orange vanishes on the pumpkin ground), and the pattern drawn over the title bands and the footer (`PATTERNS`: paw prints, snowflakes, hearts, eggs, beach, pumpkins, none). `classic` is the Wix identity and the default; the others are seasonal: `christmas` (red, snowflakes), `valentine` (pink, hearts), `easter` (lilac, eggs), `summer` (sea blue, beach), `halloween` (pumpkin orange, pumpkins and bats). The admin chooses the active theme and may change the colour and the pattern of each one; the choice is stored as JSON in the `settings` table (key `theme`) and `Base.astro` writes it in the head of every page as `--band-*` custom properties, which are the only thing `global.css` reads: never write the main colour as a literal or bring back a `--teal` token, use `--primary`. `--primary-bright` is a brighter shade computed from it in CSS (bars beside and under titles, link underlines, list markers, current menu entry); `--primary-pale` is a very light tint computed the same way (soft grounds of lists, tiles, hovered and selected entries); the logo green (`--green`, `--green-pale`) is left to the states that mean "done" in forms. Small accents placed on a ground of the main colour use `--band-accent`, not `--sand`. A colour is refused when white text would not be readable on it (`isBandColor`). To add a theme: an identifier in `THEME_IDS`, its entry in `THEMES`, its name in both languages of `src/i18n/admin.ts`; same steps with `PATTERN_IDS` and `PATTERNS` for a pattern (a white SVG tile).
- Styles: `src/styles/global.css` for the public site (design tokens first, then one block per component), `src/styles/admin.css` for the admin; the two are independent. In the admin a `.table` becomes stacked rows under 720 px: give the cell that names the row `table__main` and a `data-label` to the cells that need their column name. Home tile photos are anchored to the top (`object-position`) because the sources are portraits.
- To take screenshots with headless Chrome, pass `--accept-lang=<locale of the URL>`: otherwise the first-visit language redirect sends every URL to the browser's language.

## Migration data (`migration/`)

- `wix-export/*.csv` — the four Wix collection exports, source of truth for animals.
- `content.json`, `seo-baseline.json`, `urls.json`, `social-links.json` — output of the crawl. English and French animal descriptions come from the crawl because Wix does not export translations; they are Wix machine translations, only partly reviewed.
- `translations/{locale}/` — hand-written translations: `animals*.md` (one `### collection/slug` section per animal) and `pages/{slug}.html`. German was translated from the Romanian originals. Page files also exist for Romanian and English where the Wix text had no usable structure (the cat care guide, split into headed sections with the original wording, and in French translated again from the Romanian because the Wix French was a shortened, softened rewrite (French alone says "specialised shops" instead of naming Hornbach, on the owner's decision); the adoption guide `cum-pot-adopta` in English, and in Romanian since the owner aligned the four languages (no donation asked at adoption, home visit always, the "send your application" line everywhere: the Romanian file is the Wix text plus that line); the found-animal page `ai-gasit-un-animal`, with headings added in the four languages and its contract shown as a `.download` block; the about page `despre-noi`, with headings, key figures (`.facts`), a pull quote and a closing appeal with a donate button (`.appeal`); the sanctuary page `proiect-2022`, cut into `.story-intro`, `.chapter` sections and `.story-close`, in the four languages; the activity report `raport-2024`, which Wix only shows as two page images: its text is transcribed from the image of each language, German from the Romanian, with key figures added at the top; the volunteering page `voluntariat`, where Wix still gives the old 2 % rate of the income tax redirection instead of 3.5 %): they replace the crawled text, so after a new crawl compare them with the Wix page and carry over any change made there. `fixes.json` corrects Wix machine translations (altered animal names, wrong phrases, and the corrections of the full review of the English and French animal texts against the Romanian); `"key": "*"` applies to every animal of a language. A replacement must not be found again in its own result, so that a second import changes nothing; a text that needs more than phrases replaced is rewritten in `animals.md` instead. The post-payment page `donation-thank-you-page` has a file in the four languages: the Wix body was an unfilled template ("Thank you, Donor Name").
- Animal SEO fields are generated by `src/lib/seo.ts` from structured data only (no age, nothing from the free text) and stored, so the admin can override them.
- `raw/` and `media/` are not versioned; `pnpm crawl --media` regenerates them.

## Performance

Checked with Lighthouse on the build (5 October 2026: 91 to 97 on a simulated phone, Wix 67 to 74). What keeps it there: the image that is the largest element of the first screen carries `fetchpriority="high"` (hero, first card of a list, first photo beside a text, main photo of an animal or a campaign), every image has its size in the markup (`sizeBodyImages` adds it to stored page bodies), the logo of the public pages is `src/assets/logo.webp` (twice its displayed size, served under a hashed name), and text is compressed by nginx, not by Node. White text on the Wix orange of the buttons has a contrast of 3.7:1, below the 4.5:1 of WCAG AA: kept as the identity colour, the owner decides.
